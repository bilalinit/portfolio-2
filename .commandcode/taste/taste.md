## Verification workflow
- No test suite — verify changes with `npx tsc --noEmit` plus loading pages at localhost:3000. Confidence: 0.9
- Hand-off step before commit: after automated checks pass, the user likes to manually test the feature themselves — start both servers in the background with real config (backend `uv run main.py` on :8000, frontend `npm run dev` on :3000), probe that both respond (backend `/health`, frontend landing page), then hand off and wait; the user will say when to commit. When they ask to test "what we have deployed", that means parity with origin/main: kill the running dev-server shells first, `git checkout main`, restart both servers from `main`, verify, then hand off — never leave stale servers running off the old branch when switching. The cycle is symmetric: when the test session ends, the user asks to kill the servers and switch back to the feature branch (`chat-agent`) to resume work — dev servers are ephemeral to each testing session, and the feature branch is always restored as the working branch before development continues. The user kicks off these test sessions with terse commands like "run both server" — treat that as: start both servers in the background (frontend if not already up, plus backend), probe that both respond, then hand off. Confidence: 0.9
- Backend (FastAPI/uv) verification pattern: transient unit tests in the scratchpad run via `uv run python` (fake monotonic clock, no model/network calls), then live-test against a locally booted server on a spare port with a dummy API key + unreachable `BASE_URL` so allowed requests fail fast (502) without spending Gemini quota; curl/powershell burst to exercise limits and inspect status codes, headers (Retry-After, CORS), and body shape. Confidence: 0.7
- Repo lives on an exFAT drive (D:, external disk): `npm run build` / `next build` always fails with a spurious EISDIR/readlink error — a documented Next.js issue on non-NTFS filesystems, not a code problem. Never use a production build as a verification/merge gate; tsc + dev-page-load is the gate. Confidence: 0.95
- Windows environment: in interactive PowerShell chain with `;` (not `&&`), but the default shell_command shell is cmd.exe where `;` does NOT separate commands — the commands get merged into one argument. Issue one command per shell_command call (or use the powershell tool explicitly). Never edit files via `Set-Content` pipelines (Turbopack file locks). Confidence: 0.8

## Git workflow
- NEVER add a `Co-authored-by: CommandCodeBot` trailer (or any AI co-author attribution) to commit messages. User explicitly banned it after seeing CommandCodeBot rendered as a co-author on GitHub. Confidence: 0.95
- Standard delivery step the user asks for after finishing work on a feature branch: commit on the current branch, merge into `main`, and push to remote (e.g. "commit this to this branch and also merge it to main and push to remote as well") — but only when the request explicitly names merge/push. A bare "commit this to this branch" means commit only on the current feature branch: no merge to `main`, no push (user: "Not the merging with main yet and commit this to this branch") — never bundle merge/push into a commit-only request. Repo flow is feature branch → `main`, with `dev`/`backup` branches also present; after the merge+push, restore the feature branch as the working branch. Confidence: 0.75
- User explicitly wants git operations done "securely": never force-push; on push rejection, fetch and inspect the divergence, merge remote history into local (clean merge, no history rewrite), then push as a fast-forward. Prefer `--ff-only` merges when the target is a strict ancestor. Confidence: 0.75
- When pushing, syncs all active branches to origin with upstream tracking set (`main` + current feature branch + `dev`); stale archive branches (e.g. `backup`) stay local-only. Confidence: 0.6
- After a push the user double-checks exact local/remote sync ("Is local main and remote main exactly the same?") — answer git-state questions with fresh evidence, never from memory: `git fetch origin`, compare divergence both directions (`git log origin/main..main` and `git log main..origin/main`), and confirm identical SHAs via `git rev-parse`. Confidence: 0.6
